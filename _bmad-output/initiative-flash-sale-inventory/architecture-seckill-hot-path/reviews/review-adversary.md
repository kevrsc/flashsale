# Adversarial review — Seckill hot-path architecture spine

Spine reviewed, not edited: `architecture-seckill-hot-path.md` (draft, updated 2026-10-14).

Method: for each candidate hole, build two units one level down that each obey every current AD to the letter, and show they still cannot be dropped into one system. A clash an existing Rule already forbids is not a hole. The PRD is the vocabulary this spine must not contradict; it is not a second rulebook.

**Verdict: fail.** A gateway that obeys AD-6 and a lifecycle feature that obeys AD-8 return different answers after close. A qualify feature that obeys AD-4 and an order feature that obeys the JSON convention never write the order, so the build fails. A close command and the report publisher each publish `sale.close-report` with a different remaining count.

## Findings

### 1. Two flags cannot tell closed from not open, and the allotment key can be the live counter

- **Severity:** critical
- **Disposition:** autofix
- **Pair:** edge-admission feature and sale-lifecycle feature; pool script and close command
- **Location:** AD-1, AD-6, AD-8, paradigm ("Reads of sale state never call the script")
- **trigger_condition:** The sale has five states the answers depend on: not open, open with stock, open and sold out, closed with stock left, closed and sold out. AD-6 lets the gateway read exactly two flags and still requires it to answer `not_open`, `closed`, or `sold_out` without calling the sale application. Two flags have four combinations. AD-8 adds a third flag, `closed`, and does not say the gateway reads it, does not say close clears `open`, and does not say `allotment` and `remaining` are different keys. AD-1 reserves `open`, `sold_out`, and `remaining` for the Lua script and does not mention `closed`. No rule names the keys or the answer order. The paradigm forbids a read that calls the script; no Rule says a remaining read is a GET.
- **Construction:** Edge admission uses only the two flags AD-6 names, as booleans, and a total map onto the three answers: `open=0, sold_out=0` → `not_open`; `open=0, sold_out=1` → `closed`; `open=1, sold_out=1` → `sold_out`; `open=1, sold_out=0` → forward. It never writes. Lifecycle, inside the one script, keeps three booleans. Start sets `open=1` and leaves `sold_out=0`. The decrement that hits zero sets `sold_out=1` and leaves `open=1`. Close sets `closed=1` and `open=0` so a script that guards on `open` stops decrementing, and it leaves `sold_out=0` when stock remains. The script answers `closed` whenever `closed=1`, which is how it still returns that answer, as AD-6 requires. Separately, the pool script treats the allotment key as the live counter: load sets it to 100, and each qualification decrements it. Close treats the allotment key as the immutable loaded quantity and decrements a second key, `remaining`. Both are legal. AD-8 says the last load sets the allotment key. AD-1 says the remaining count changes only in the script. Neither sentence says they are two keys or one.
- **Clash:** After close with stock left the hash is `open=0, sold_out=0, closed=1`. The edge answers `not_open`. The script answers `closed`. The same attempt is before-start at the gateway and after-close at the sale application. On the counter, close reads `remaining`, which the pool script never wrote, and publishes 0 while the live allotment key still holds 40. A read feature EVAL's the attempt command to learn `remaining`, because that is the only command that is allowed to touch the count, and a concurrent qualification runs the same command.
- **Smallest AD change:** Add one sale record to AD-1, and point AD-6 and AD-8 at it. Redis hash `sale` holds `itemId` (string), `allotment` (integer), `remaining` (integer), `open` (`0` or `1`), `closed` (`0` or `1`), `soldOut` (`0` or `1`), and `closeRemaining` (integer, absent until the first close). `allotment` is set by load and does not change after that. `remaining` starts equal to `allotment` and is the only field the attempt decrements. The same script is the only writer of all of those fields, including `closed`. Commands are `load`, `start`, `attempt`, `close`, and `ack`. `load` runs only when `open=0` and `closed=0`; it sets `itemId`, `allotment`, `remaining=allotment`, and `soldOut=0`. `start` runs only in that same state, sets `open=1`, and does not change `remaining`. After `closed=1`, `load` and `start` change nothing. `close` sets `closed=1`, stores `remaining` into `closeRemaining` only when that field is absent, and does not change `remaining` or `allotment`. The attempt that decrements `remaining` from 1 to 0 sets `soldOut=1` in that same execution and still returns `qualified`. Answer order, in the gateway and in the script: blank `userId` → `unidentified`; else `closed=1` → `closed`; else `open=0` → `not_open`; else `soldOut=1` or `remaining=0` → `sold_out`; else the script decrements. The gateway and any other reader use `HGET` on `sale`. They do not `EVAL`.
- **potential_consequence:** A closed sale is announced as not open, and the next direct attempt is judged by the other answer. Inventory is told the pool is empty while units remain, or is told the original allotment is still remaining after those units were taken. A remaining read takes the qualification path.

### 2. The pending entry is an id, and the order row is a document

- **Severity:** critical
- **Disposition:** autofix
- **Pair:** qualify/relay feature and order-insert feature
- **Location:** AD-1, AD-4, AD-5, Consistency Conventions (Data and formats), AD-3 dependency diagram (`qualify --> pending`, `orders --> pending`)
- **trigger_condition:** AD-4 says the script records the qualification id, the Kafka key and the order primary key are that id, and the relay republishes ids still pending. AD-5 says `sale.qualification` carries the qualification id. The convention says the JSON properties are `answer`, `qualificationId`, `saleId`, `userId`, `itemId`, and `remaining`, and it does not say which message carries which. AD-1 forbids a per-customer set. Nothing says the pending value, the Kafka value, and the order columns are one document, or that only the order consumer inserts the row.
- **Construction:** Qualify stores a Redis SET of UUID strings, publishes `sale.qualification` with that id as the key and the same string as the value, and keeps `userId` out of Redis so the script cannot be said to hold a per-customer set. The relay republishes those ids. The order consumer reads the same topic and deserializes the value as a JSON object with `qualificationId`, `saleId`, `userId`, and `itemId`, because those are the convention's property names and the order is what another service continues from (FR-7). A value that is not that object is not inserted. The insert it does perform is idempotent on the id. The report publisher, allowed by AD-3 to read an order row and not forbidden to write one, inserts a stub row whose only column is the id so the build's "id with no order row" check passes, then the consumer's `INSERT` finds the row and skips the customer fields.
- **Clash:** Every qualified id stays pending. The relay republishes the bare string, which still fails the JSON check, so the order row is never the document the consumer would write. Where the stub lands first, the id has an order row, the build passes, and `userId` and `itemId` are empty. Payment and fulfillment consume a row they cannot continue from. The two features do not share a single in-memory shape they could reconcile at runtime, because the relay no longer has the fields the first publish dropped.
- **Smallest AD change:** Tighten AD-4. One qualification document, JSON, fields exactly `qualificationId` (lowercase UUID, 8-4-4-4-12), `saleId` (the string `sale`), `userId`, and `itemId`. The script writes that document into Redis hash `pending` under field `qualificationId` in the same execution as the decrement. The `sale.qualification` key is `qualificationId`. The value is those JSON bytes, unchanged, with no schema-registry envelope. The relay republishes that value. `saleId` is not a second sale; more than one open sale stays deferred. Storing `userId` and `itemId` on that one document is not a per-customer set. Table `orders` has primary key `qualification_id` and not-null columns `sale_id`, `user_id`, and `item_id`. The order consumer is the only inserter, and the insert is idempotent on that primary key. After the insert commits, the consumer calls the script command `ack`, which deletes that pending field. The attempt response is sent before this publish; the publish does not delay it. A Java `SREM` is not required: `ack` is how AD-1 and AD-4 both hold.
- **potential_consequence:** The learning burst qualifies 100 units and the build fails for missing orders, or it passes on stub rows and the downstream order has no customer and no item. A second writer locks the stub in place.

### 3. Close and the report publisher both own the close report

- **Severity:** critical
- **Disposition:** autofix
- **Pair:** sale-lifecycle feature and report-publisher feature
- **Location:** AD-3, AD-5, AD-8, capability map row FR-9
- **trigger_condition:** AD-8 says close publishes one close report of the remaining count, and a second close publishes that same count. It does not define the count. AD-3 says the report publisher may read the order row and publish to Kafka. The capability map gives all of FR-9, including the close report, to the report publisher. `remaining` is one of the undifferentiated JSON properties. Nothing says which component publishes which topic, or that a qualification still in `pending` is already taken.
- **Construction:** Lifecycle, on close, reads Redis `remaining` and publishes `sale.close-report` as `{"remaining": 40}` after 60 of 100 units were qualified and 20 of those 60 are still pending (40 orders committed). It does not publish qualification reports. The report publisher reads `orders`, publishes one `sale.qualification-report` per row, and also publishes `sale.close-report` because it owns FR-9. Its remaining count is `allotment - count(orders)`, which is 60. Its qualification report includes `remaining` as the pool left after that row, because the property exists. A repeated close from lifecycle sends 40. The publisher's close sends 60. Each feature publishes the same body on its own retry, so each obeys "a second close publishes the same remaining count" for its own count.
- **Clash:** Inventory sees two close facts, 40 and 60, for one sale. Qualifications plus the publisher's remaining are 120 against an allotment of 100, so posting both facts removes units twice or leaves 20 units that were already taken. The qualification report's `remaining` is a third meaning of the same property. The map and AD-8 assign the close report to different owners, so deleting either publisher leaves the other in place.
- **Smallest AD change:** Tighten AD-8 and AD-3, and correct the FR-9 map row. `remaining` in a close report is `closeRemaining` from finding 1: the Redis pool at the first close. Units still in `pending` are not remaining. Only the `close` command publishes `sale.close-report`. The body is exactly `{"saleId","itemId","remaining"}`, and the Kafka key is `saleId`. A second close republishes that stored body. Only the report publisher publishes `sale.qualification-report`, and only by reading an `orders` row. The body is exactly `{"qualificationId","saleId","userId","itemId"}`, and the key is `qualificationId`. It does not publish a close report and does not insert an order. A failed publish is tried again; the retry sends the same JSON.
- **potential_consequence:** Warehouse stock moves by the wrong number. A repeated close, which the PRD says carries the same remaining count, carries two counts. Qualification reports and close reports cannot be applied together.

### 4. The attempt and the inventory commands have no shared request

- **Severity:** high
- **Disposition:** autofix
- **Pair:** gateway feature and qualify API; lifecycle command feature and the script's `load`
- **Location:** AD-6, AD-8, Consistency Conventions (State and cross-cutting; Data and formats)
- **trigger_condition:** AD-6 fixes the response `answer` and when `qualificationId` is present. It does not fix the method, the path, the status, or the request fields. The convention says the edge forwards `userId` and a missing `userId` is `unidentified`, and it does not say whether blank is empty or whitespace. `saleId` and `itemId` sit in the same property list as the response fields. AD-8 says the inventory service calls the sale application to load, to start, and to close, with no path and no body. The glossary says `not_open` is the answer before the start signal, so a mismatch cannot be smuggled out as `not_open` without contradicting the PRD.
- **Construction:** The gateway calls `POST /qualify` with `{"userId","itemId"}`, expects HTTP 200 plus the AD-6 JSON, and treats a missing property `remaining` as a malformed response because the convention lists it. A `userId` of `" "` has length greater than zero, so the gateway forwards it and the script qualifies that customer; the gateway's blank check is length zero only. The qualify API listens on `POST /api/attempts` with `{"userId","itemId","saleId"}`. It answers `unidentified` when `saleId` is absent, and it treats whitespace as blank, so `" "` takes no unit. Lifecycle exposes `POST /admin/load` with `{"qty":100}`. The script's `load` reads `itemId` and `allotment` and leaves `remaining` unset when `qty` is the only field.
- **Clash:** The gateway never reaches the qualify route. A client that does reach it is `unidentified` on every attempt because the gateway does not send `saleId`. The same `" "` attempt qualifies through the gateway's reading and takes no unit through the script's reading. Load returns success to the inventory service and the pool stays empty, so the next start opens a sale that is immediately sold out, or stays not open if `remaining` was never set. Requiring `remaining` on the attempt response drops a legal AD-6 body.
- **Smallest AD change:** Tighten AD-6 and AD-8. The attempt is `POST /attempts` on the sale application, JSON body exactly `{"userId"}`. Every answer is HTTP 200. The body is exactly `{"answer"}` plus `qualificationId` only when `answer` is `qualified`. `userId` is unidentified when it is absent, empty, or whitespace only; any other `userId` is forwarded unchanged. The gateway applies that check and does not call the sale application. The script applies the same check before a decrement when an attempt arrives past the edge. The recorded `itemId` is the loaded `itemId`. The attempt does not select an item, and a different `itemId` in the body does not change the answer. Inventory calls the sale application directly: `POST /sales/load` with `{"itemId","allotment"}` where `allotment` is an integer zero or greater, `POST /sales/start` with `{}`, and `POST /sales/close` with `{}`. An applied command is HTTP 200. A `load` or `start` that finding 1 refuses is HTTP 409 and changes nothing. These responses are not the five attempt answers.
- **potential_consequence:** The crowd never reaches the pool, or a space qualifies in one process and is rejected in the other. The inventory service loads an allotment the script does not see, and the sale opens with an empty pool.

### 5. An open breaker may finish the report by dropping it

- **Severity:** high
- **Disposition:** autofix
- **Pair:** circuit-breaker feature and report-publisher feature
- **Location:** AD-7, AD-3, AD-4
- **trigger_condition:** AD-7 says an open breaker retries or sheds the order insert, the report publish, and telemetry export. Shed of the report grants no extra unit, which is all the Prevents line requires. FR-10, which AD-7 binds, says a failed report is retried. The pending relay republishes a qualification id until an order row exists. Nothing republishes a report once a publisher has moved past that row. Telemetry export is the call a down collector is allowed to lose (AD-9).
- **Construction:** The breaker wraps the report publish. When it is open, the fallback returns immediately without a Kafka send, so the publisher thread is not stalled. The report publisher walks `orders` in primary-key order. On that fallback it advances its cursor, because the call returned and AD-7 lists shed as a completed outcome. It does not decrement and it does not mark the row failed. The order insert, if shed, leaves the id in `pending`; the relay republishes it; that half is already closed by AD-4.
- **Clash:** The qualification report is never sent, and the next pass does not select that order. Inventory never learns of the unit. A second pass after the breaker closes cannot tell a shed report from a published one. The order row exists, so the build's order check passes. The two features obey AD-7 and still drop the fact FR-9 says is delivered during the sale.
- **Smallest AD change:** Tighten AD-7. An open breaker may shed telemetry export only. The report publisher retries `sale.qualification-report` until the producer ack. A shed or a thrown publish leaves that order eligible on the next pass. The order insert is retried by the AD-4 relay until the row exists; the consumer does not ack the qualification record past an insert that did not commit, and it does not `ack` the pending field before that commit. The gateway's reactive breaker wraps gateway routes other than the attempt forward. The attempt response remains the AD-6 JSON.
- **potential_consequence:** Qualifications equal the allotment and every id has an order, and the inventory service still never receives the qualification reports. SM-C1 is the outcome AD-7 currently allows.

## Not a hole

These pairs were built and then dropped, because a unit that produces the clash is already breaking a Rule.

- Java `SREM` of the pending id versus a consumer that refuses any write outside the script. AD-1 and AD-4 are both satisfied when the consumer calls `ack` on that same script after the insert commits. A process-level `SREM` does not obey AD-1. Finding 2 names `ack` so the two rules stay one path.
- A second decrement from a breaker retry, a breaker around the Lua script, or a shed that grants another unit. AD-7 forbids all three. The order id survives a shed insert because of the relay. The report does not; that is finding 5.
- A third service inserting the order, RabbitMQ, a per-customer cap, a Postgres read to decide the attempt, a CDN as a second filter, a second metrics product, a sale clock, or a payment return. AD-2, AD-5, AD-1, AD-6, AD-9, and Deferred already forbid them.
- Two consumer groups on `sale.qualification`. AD-2's one consumer group forbids the second. The group id string is unnamed and is not a second feature's contract until a second consumer exists.

## Deferred audit

Not holes. Each line still has a single owner, or it is a product non-goal.

- CDN vendor, cache keys, and TLS. AD-6 keeps the CDN from being a second filter. Cache keys here are the CDN's, not the `sale` hash in finding 1.
- The numeric admission rate. Only the gateway chooses it. The sale script does not read it. Flag answers and the script still decide the pool.
- Inventory's internal stock posting. Findings 2 and 3 are the report bodies this spine owes. The posting rule stays with the inventory service.
- More than one open sale. Finding 2 fixes `saleId` as `sale` so two features cannot invent different ids while this stays deferred.
- Returning a unit when payment does not finish. No command increments `remaining`.
- A sale clock inside this service. Start and close remain the inventory service's calls.

## What held

The hot-counter split holds. One script decides the pool, the attempt answer comes from that decision, Kafka carries the qualification id, and Postgres stores one order per id. AD-1's ban on a second writer of the count, on a Postgres read for the attempt, and on a per-customer cap matches FR-3 and FR-6. AD-5's three topic names, and the ban on RabbitMQ, are already a shared contract. The five answer strings match the glossary. The order primary key, the build failure when an id has no order, and "not granted again until the row exists" match FR-7 once finding 2 says what the row contains. AD-3 keeps the inventory service off the attempt. JaCoCo at 95% line and 95% branch, and tests for two sale instances against one Redis, are already one bar.
