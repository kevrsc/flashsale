- (constraint) Inherited from the final PRD: this service deducts inventory and sends an order event; payment, fulfillment, and completing the purchase stay in other services.
- (constraint) Inherited from the final PRD: a customer is recognized by the user ID of an account this service does not create or manage.
- (constraint) Inherited from the final PRD and addendum: on a successful order a Kafka client writes the deduction and posts an order event to a Kafka topic. The units deducted are the smaller of the request, the inventory pool, and the units left under the customer limit of 3.
- (constraint) Inherited from the final PRD: empty pool yields sold out even during the one-hour wait; the wait blocks another order while the pool is above zero; a customer with no units left is refused. No deduction of a unit that was not available. The service must show request counts and database query and update counts. How database contention is handled is not yet chosen.
- (decision) User chose the coaching path.
- (decision) The spine is the build contract. An additional walkthrough is required so the user can explain the architecture to other people. The walkthrough is produced at the end, not instead of the spine.
- (decision) Paradigm is the transactional outbox. Binds the inventory deduction and the outbound order event as one committed outcome. Prevents one unit writing the database and another publishing Kafka so a deduction can exist without an event, or an event without a deduction.
- (version) Spring Boot 4.1.1 is the stable release shown on spring.io as of 2026-09-29. Spring Modulith 2.1.1 is the stable release on spring.io and its 2.1.1 notes upgrade to Spring Boot 4.1.1.
- (decision) Starter is Spring Initializr on Spring Boot 4.1.1 with Spring Modulith 2.1.1. Event externalization mode is outbox, so the publication row commits in the same database transaction as the inventory deduction and is sent to Kafka after that commit. Binds the runtime and the outbox mechanism. Prevents a second stack that publishes to Kafka outside the deduction transaction. Official Modulith docs say the default listener publish is not this outbox mode.
- (decision) Order event contract: one Kafka topic inventory.order-accepted. This service creates the order id and uses it as the message key. Body fields are order id, customer user ID, item, and units deducted. The original requested quantity, payment, and fulfillment are absent. Binds this service and the separate order service. Prevents the order service from requiring a different payload before it can continue the purchase.
- (decision) Database is PostgreSQL 18.6, current stable on postgresql.org as of 2026-09-29, hosted in Docker. The inventory row and the outbox rows live in that one database and commit in one transaction. Binds persistence. Prevents the outbox from living in a different store than the inventory deduction.
- (version) Official Docker Hub image tag postgres:18.6 exists for the PostgreSQL 18.6 release. Binds the container image. Prevents a builder from using the floating latest tag or the PostgreSQL 19 beta image.
- (decision) The inventory pool changes only by a conditional update in the same transaction as the outbox insert. The update applies only when the row still holds the units being deducted, and those units are the smaller of the request, the pool, and the units left under the customer limit. If no row changes, the order did not succeed and no outbox row is written. Binds pool mutation. Prevents two requests from both reading the same remainder and both deducting it.
- (decision) Admission to PostgreSQL is bounded. Only a small number of requests open a transaction on the item row; the rest wait in the application or are turned away at the edge without a transaction. The page waits for its turn and is not told sold out while the pool is above zero. Jitter applies only to a retry after the gate turns a request away. After a conditional update finds the pool empty, a sold-out hint answers later requests without a transaction; the row remains the authority for every deduction. In a transaction that updates both, lock the customer row and then the item row. Binds contention handling. Prevents a connection storm on one row, a second stock count, first-request jitter, and a deadlock from opposite lock order.
- (decision) The landing page is served by the same Spring Boot application that owns the admission gate and the conditional update. Binds the user-facing entry. Prevents a second client from deducting inventory through a separate path.
- (decision) Kafka runs in Docker beside PostgreSQL, using the official image apache/kafka:4.3.1, a current stable download on kafka.apache.org as of 2026-09-29. The 4.4.0 tags are release candidates and are not used. Binds the broker runtime. Prevents a builder from pointing the outbox publisher at a different broker or at a release-candidate image.
- (decision) The Spring Boot application runs on the host. Docker Compose runs PostgreSQL and Kafka and publishes their ports to localhost. Binds local runtime topology. Prevents one configuration from using Compose service names while another uses localhost.
- (decision) Two Spring Modulith modules. The inventory module owns the conditional update, the customer and item rows, the admission gate, and the outbox publication. The page module depends on the inventory module and only renders the landing page and the outcomes the inventory module returns. The inventory module does not depend on the page, and the page does not write the pool. Binds dependency direction. Prevents a controller from deducting inventory on its own and the domain from importing web types.
- (decision) Order event wire format is JSON. The value is one object with string orderId, string userId, string itemId, and integer unitsDeducted. No schema registry and no shared Avro or Protobuf file. Binds the bytes on inventory.order-accepted. Prevents the order service from decoding Avro or Protobuf, or from expecting different property names.
- (decision) The landing page collects the customer user ID. The inventory module treats that value as the account's user ID and does not authenticate it or look it up in a user table. Binds how an order identifies the customer. Prevents this application from owning accounts, and prevents the inventory module from requiring a user ID supplied by a proxy or a separate account service.
- (decision) The inventory module alone records sale counts and writes the running totals to the application log. A request is an order attempt that reaches inventory, including success, the one-hour wait, refusal, sold out, and an admission-gate turn-away. Opening the page without ordering is not a request. Query and update counts include every database statement this application runs, including the outbox publisher. The counts are process totals, not rows in PostgreSQL, and they reset when the application restarts. Binds what the two modules report for traffic and database usage. Prevents a second tally in the page, a counter table on the hot path, and a metrics endpoint in place of the log.
- (decision) One customer row per user ID in PostgreSQL. The row stores the units that customer has successfully ordered and the earliest time they may order again. A successful order writes both in the same transaction as the pool deduction. The next-allowed time is PostgreSQL's clock plus one hour. When an admitted transaction finds no row for that user ID, it inserts the row in that transaction before it locks the item row. The page does not compute the wait. Binds customer state and the one-hour clock. Prevents a per-order history, an application clock, and a customer list that must be loaded before anyone can order.
- (decision) The landing page is a server-rendered Thymeleaf form. spring-boot-starter-thymeleaf is on the Spring Boot 4.1.1 BOM. The page module owns the template and the controller. The shopper enters a user ID and a quantity. The form submits a fixed item id for the one item row seeded in PostgreSQL. The controller calls the inventory module in-process and renders the outcome inventory returns. Inventory alone applies the smaller of the requested units, the pool, and the units left under the customer limit. Binds the browser entry and the item scope. Prevents a JSON client in the browser and a second item catalog.
- (decision) Item and customer tables are created by Flyway through spring-boot-starter-flyway on the Spring Boot 4.1.1 BOM, plus Flyway's PostgreSQL module. The inventory module uses JDBC for those rows. A Flyway migration inserts the single item and its starting pool. Outbox tables are created by Namastack's JDBC starter, namastack-outbox-starter-jdbc 1.7.3, pulled by spring-modulith-starter-namastack 2.1.1. Our migrations do not create the outbox tables. Hibernate does not create or alter schema. Binds schema ownership. Prevents Hibernate ddl-auto and a hand-copied outbox DDL.
- (version) Java version is 17, the current default on start.spring.io as of 2026-09-29. Spring Boot 4.1.1 requires at least Java 17. Binds the Initializr language level.
- (decision) The inventory module publishes inventory.order-accepted through spring-modulith-events-kafka 2.1.1, which brings spring-kafka 4.1.1. Namastack outbox mode still commits the publication row with the deduction and sends it after commit. Binds the Kafka client. Prevents a hand-written Kafka producer beside Modulith externalization.
- (decision) The only environment in this spine is local. The Spring Boot application runs on the host. Docker Compose runs postgres:18.6 and apache/kafka:4.3.1 and publishes their ports to localhost. Application configuration uses localhost, not Compose service names. A hosted or second environment is deferred until a launch target exists. Binds deployment. Prevents a second topology in this build.
- (direction) Deferred with revisit conditions: admission-gate concurrency number, revisited when a load run shows connections queueing on the item row; order-id generation algorithm, revisited only if an order service must parse the id, which until then is a unique opaque string; starting pool quantity and item-id characters, revisited when the Flyway seed is written and both must come from that one seed; log-line wording, revisited if a scraper is added; the form HTTP path, revisited inside the page module; a hosted environment, revisited when a launch target exists; restock and clearing the sold-out hint, revisited only if the pool can increase after it hits zero.
- (decision) Reviewer gate tightenings. A missed conditional update rolls the transaction back and is not sold out while the pool is above zero. Wait and the customer limit are checked under the customer-row lock before the item update. Customer user id is a unique key and the losing insert continues on the existing row. The page gets the item id from inventory and runs no SQL. Shopper outcomes are only in process, wait one hour, sold out, refused, and not accepted. A gate turn-away is a page retry with jitter, not a rendered outcome. The order event is exact four-field JSON, unitsDeducted is the deducted amount, the order id is stored in the commit and never reused, and the order service treats it as an idempotency key. Inventory alone publishes, via the Modulith event. One Boot process. Local ports are PostgreSQL localhost:5432 database flashsale user flashsale password flashsale, and Kafka localhost:9092. Compose creates the topic. Build is Gradle Groovy. Boot parent coordinate is 4.1.1, not the Initializr token 4.1.1.RELEASE. Stack adds webmvc, jdbc, postgresql driver, spring-boot-kafka, and flyway-database-postgresql 12.4.0 as confirmed against the Boot 4.1.1 BOM.
