Flash-sale inventory

This service decides who receives a unit when more people want the item than the inventory pool holds.

Payment and shipping stay in other services. They begin only after this service has deducted a unit and sent an order event.

The architecture spine is the contract the build follows. These slides explain it.

Two modules, one application

The page collects a user id and a quantity. Inventory decides what happens to the pool. The page cannot write the database.

What the shopper can be told

  • The order is in process.
  • Wait one hour before ordering again.
  • The item has sold out.
  • The order is refused, because this customer has no units left under the limit of 3.
  • The order was not accepted, because the quantity or the user id was blank.

Sold out wins when the pool is empty, even during the one-hour wait.

The locks decide the number

The transaction locks the customer row, then the item row. It reads both before it chooses a number.

The units taken are the smaller of what was asked, what the pool still holds, and what this customer has left of the limit of 3. One customer has one row. The wait ends at the database clock plus one hour.

One commit, then the event

The outbox row is the order event, stored in the database with the deduction so the event cannot exist without the deduction.

A successful order writes three things in one database transaction: the customer row, the item pool, and the outbox row.

Kafka is told after that commit, and after the page has the outcome. If the pool update matches no row, the whole transaction is discarded. The customer does not keep units that were never taken.

What the other service receives

The topic is inventory.order-accepted. The message is JSON with four fields: order id, user id, item id, and the units actually deducted.

The order id is the message key. Delivery can repeat. The same order id is the same purchase, not a second one.

Many people, one item row

Only a small number of orders open a database transaction on that item. The others wait in the application and retry. A waiting shopper is not told the item is sold out while units remain.

The item row is the only stock count. A sold-out hint may answer later requests after the row is empty. The hint never deducts a unit.

Where it runs

One application process on the host. PostgreSQL and Kafka run in Docker and are reached on localhost.

This architecture stops at that machine. A hosted environment waits until there is a launch to aim at.

Left for the build

  • How many transactions may touch the item row at once.
  • The starting number of units, written once in the database seed.

Those choices sit inside one module. They do not change the commit, the shopper outcomes, or the order event.
