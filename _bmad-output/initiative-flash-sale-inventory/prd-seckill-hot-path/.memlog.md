- (event) New PRD session opened for a rewrite that pulls the hot item out of the normal order path, in the manner of large-platform seckill systems. The finalized PRD at prd-flash-sale-inventory stays as-is.
- (decision) This service is separate from the standard inventory service. It receives an allocated allotment for one item and sells that limited quantity to a rush of customers.
- (decision) Follow the large-platform seckill pattern that pulls the hot item off the normal order path. Technology already in the service may be removed if that pattern does not need it, and missing pieces may be added.
- (assumption) Customers are already authenticated and authorized to take part in the sale. This service does not manage accounts.
- (assumption) The flash sale starts when the inventory service allocates a quantity for a particular item. The user offered this as a guess and left it open to correction.
- (decision) About 100,000 customers may try to buy from a pool of 100 within minutes of the start. One or many instances may run. They share one quantity pool, and that sharing is done in the persistence layer.
- (decision) The main inventory service must adjust its stock from what this service reports. A report is required. Whether it is sent as each sale happens, on a period, or when the sale ends is still open.
- (decision) Production concerns stay in scope: an OpenTelemetry collector, Prometheus scraping, Grafana, meaningful logging, and test coverage, plus similar orthogonal concerns.
- (decision) Stakes are a learning model of the production shape. The user does not intend to launch or operate this as an internal service. The PRD should describe that production shape at learning-model length.
- (decision) Working mode is fast path. Remaining gaps are asked in one pass, then the PRD is drafted with assumption tags where the user did not decide.
- (event) Published seckill notes recorded in the addendum. Preloading an isolated quantity matches the user's guess. Reporting to inventory only at the end, and deducting warehouse stock on each winning click, do not match the writeups. Large-seckill guidance recommends deduct-on-order; a timed hold-and-release is described as the ordinary-commerce default.
- (decision) Nothing from the current service is kept except the orthogonal concerns already named: OpenTelemetry collector, Prometheus scraping, Grafana, meaningful logging, and test coverage.
- (decision) Modulith and the rest of the current technology are not requirements. A current choice stays only when it is the seckill implementation the user wants.
- (decision) The user requires edge filtering and rate limiting, a shared in-memory inventory count such as Redis, an async order queue such as Kafka or RabbitMQ, separation of sale-state reads from qualification writes, and shedding non-essential work. Hystrix was named as an example of a circuit breaker.
- (change) The shared pool is the in-memory count every instance uses. A disk database is not read on every click. This refines the earlier decision that sharing lives in the persistence layer: the durable order record is written asynchronously after qualification.
- (assumption) Draft PRD assumes: customers arrive through an edge and this service renders no page; load and start are separate; each attempt is one unit; the unit is taken at qualification and is not returned for unpaid orders; the inventory service closes the sale; one open sale; a customer may qualify again with no cap; reports go out during the sale and at close.
- (decision) User confirmed every draft assumption. A customer may qualify more than once while units remain, and the earlier limit of 3 stays retired. Those statements are requirements. No assumption tags remain.
- (decision) The circuit breaker is Spring Cloud Circuit Breaker backed by Resilience4j (spring-cloud-starter-circuitbreaker-resilience4j). Hystrix is not used. The breaker wraps downstream calls. The pool decrement stays on the qualification path. Recorded in the addendum. The PRD requirement stays the shed-non-essential-work behavior.
- (change) Reconciliation: addendum early sections now match the confirmed sale. The edge must keep the full crowd off the qualification path. A downstream failure must not skip the pool decrement. Tests that fail the build include the read split and the shed path.
- (decision) Set aside as document stakes, not a product ban: this is a learning model, so the PRD stays short. The service is still specified in the production shape, including many instances and the observability stack. A non-goal forbidding launch or internal operation was not added.
- (change) Review follow-up: named the answers not open, closed, and unidentified; a load during an open sale does not change the pool; the last load before start sets the allotment; empty or not-open attempts do not decrement the pool; qualification report and close report are separate idempotent facts and warehouse posting must not remove the same unit twice; build tests include FR-1 and FR-2. The order-write ending is left open.
- (decision) Every qualification has one order. The qualification id assigned at the pool decrement is the identity of that order and of the qualification report. A retry uses the same id. A qualification id with no order fails the build. The unit stays assigned and is not granted again until the order exists.
- (change) Structure pass applied. Addendum now leads with the required components and keeps the published notes. Restated sale rules were cut from the addendum. The PRD dropped the empty open-question and assumption sections and the MVP recap. FR-8 sits with the qualification rules. Named telemetry products live in the addendum operations section.
- (change) Prose pass applied. Wording now distinguishes not open from closed, names the attempt as the actor for a missing identity, and uses glossary terms for the two reports the breaker wraps.
- (event) PRD finalized
